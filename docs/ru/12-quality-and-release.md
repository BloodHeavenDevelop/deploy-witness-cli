# 12. Качество и критерии выпуска

Каждая версия получает воспроизводимую оценку качества со [стенда](11-test-bench.md)
на тех же сценариях, что и предыдущая, а релиз выпускается, только когда проходит
шлюз выпуска.

```bash
make bench-score     # последний прогон стенда по правилам против bench/baseline
make release-gate    # свежий прогон стенда + шлюз; код 1, если он блокирует
make bench-baseline  # сделать последний прогон базовым (только если он проходит шлюз)
```

`bench/dwscore` печатает таблицу и пишет `quality.json` рядом с `results.json`
прогона.

## Показатели по правилу

| Колонка | Считается по | Значение |
|---|---|---|
| `scen`, `scored` | все сценарии правила; те, чья эталонная истина подтвердилась | Сценарий с ошибкой стенда или с поведением Docker, противоречащим ему, не оценивается |
| `problems`, `found` | подготовленные проблемы | Прогноз `problem` (или план `refused` — деплой не сможет стартовать) |
| `missed` | подготовленные проблемы | Прогноз `no-problem` или `not-applicable`: сказано «чисто», хотя это не так |
| `unknown` (problems) | подготовленные проблемы | Прогноз `unknown` или `manual-check`: **не обнаружение**, и он снижает долю обнаружений |
| `clean`, `false` | подготовленные чистые ситуации | `false` — находка проблемы, которой нет |
| `unknown` (clean) | подготовленные чистые ситуации | Неизвестность, которую данные не оправдывают |
| `no-data`, `guessed` | подготовленный недостаток данных | `guessed` — вывод (в любую сторону) без нужных данных |
| `situations` | | Какие из трёх определяющих ситуаций готовят сценарии правила — `problem,no-problem,unknown` означает полное покрытие |

Итоги: **обнаружение** = found ÷ подготовленные проблемы — неизвестности стоят в
знаменателе, а не в числителе, поэтому частые ответы «unknown» его снижают;
**ложные находки** = false ÷ clean; **прогнозы unknown** — по всем сценариям;
**по спецификации** — по оценённым.

## Сравнение версий

`dwscore` сопоставляет прогон с базовым (`bench/baseline/results.json`) по каждому
сценарию: `regression` (был пройден, теперь нет), `fixed`, `changed` (другой итог, но
по-прежнему проходит), `new`, `removed`. Два прогона сравнимы только на одинаковых
сценариях, поэтому удалённый сценарий блокирует шлюз, а не улучшает показатели.

У CLI до появления итогов правил (≤ 1.4.0) нет `audit.rules`; стенд тогда выводит
итог так, как такой отчёт читали, — blocker или warning означают проблему, info или
ничего — нет, — и не передаёт ему `--project-name` (проект он выводил из каталога).
Исходная точка записана в `bench/history/1.4.0.json`: выпущенный 1.4.0 (origin/main),
оценённый на сегодняшних сценариях:

| | 1.4.0 | эта версия |
|---|---|---|
| по спецификации | 25 / 46 | 46 / 46 |
| обнаружение (unknown — не обнаружение) | 13 / 17 — 76% | 17 / 17 — 100% |
| ложные находки | 6 / 19 — 32% | 0 / 19 — 0% |
| прогнозы unknown | 0 — неизвестности не было; нерешённый порт был warning и читался как проблема | 9 — ровно все подготовленные случаи недостатка данных |
| выводы без данных (`guessed`) | 9 / 9 | 0 / 9 |

Его пропуски и ложные находки — это дефекты, исправленные в DW-80 … DW-88: свой
контейнер деплоя с `-p` читался как конфликт, отсутствующий источник с
`create_host_path: false` проходил, том, созданный вручную, не замечался, а каждое
правило, зависящее от движка, делало выводы по движку, до которого не достучалось.

## Шлюз выпуска

Выпуск блокирует любое из:

| Блокирует | Почему |
|---|---|
| ошибка стенда | Прогон ничего не доказывает, пока не работает сам стенд |
| побочный эффект аудита | Аудит не должен ничего менять на хосте |
| оцениваемый сценарий, поведению Docker в котором противоречит его описание | Нет эталона: сначала исправить сценарий |
| падающий **критичный** сценарий (`critical: true`) | Известный критичный пропуск — ложный blocker на штатном обновлении, пропущенная проблема порта, имени, тома, сети, подсети, bind или env-файла |
| падающий **регрессионный** сценарий (`regression: <задача>`) | Вернулась исправленная ошибка — см. [13](13-pilot-regressions.md) |
| сценарий, пройденный в базовом прогоне и падающий теперь | Регрессия, что бы ни говорили итоги |
| сценарий базового прогона, отсутствующий в текущем | Удаление сложного теста — не улучшение |

Рост неизвестности тоже не выдать за прогресс: сценарий, верно решённый в базовом
прогоне и ставший `unknown`, — регрессия этого сценария.

Перед выпуском: `make release-gate`. Если он прошёл, а сценарии менялись, —
`make bench-baseline` и строка в CHANGELOG о том, почему сдвинут базовый прогон.

Тот же шлюз работает в CI: workflow `bench` (`.github/workflows/bench.yml`) запускает
`make release-gate` на каждый пуш в `main` и каждый pull request и падает, если шлюз
блокирует; `bench/out/` прогона сохраняется артефактом `bench-results`. Юнит-тесты и
регрессии пилотов идут в workflow `test`.
Базовый прогон, закоммиченный в этом изменении, — прогон 2026-10-19 на
`docker:27.5.1-dind` (Docker 27.5.1, Compose 2.33.0): 46 сценариев, все по
спецификации, шлюз PASS.

# 5. Архитектура

## Поток выполнения

```
main.go
  └─ config.Load(argv, env)          флаги → Config, либо ошибка до любого действия
  └─ --commands? напечатать run.Commands() и выйти      (сам применяемый список)
  └─ logging.New(stderr, level)      диагностика никогда не попадает в stdout
  └─ audit.New(cfg, log).Run()
       ├─ model.ReadOSRelease()      /etc/os-release → идентичность дистрибутива
       ├─ pkgmgr.Detect(os, runner)  какой пакетный менеджер реально есть на хосте
       └─ для каждого выбранного раздела:
            ├─ system.Collect()      → []model.Fact
            ├─ manager.Updates()     → []model.Update
            ├─ vuln.Collect()        → []model.Vulnerability   (три источника, слитые)
            ├─ ports.Collect()       → []model.Port
            ├─ services.Collect()    → []model.Service
            └─ witnessSection()    → манифест + возможности → находки
                 ├─ manifest.Parse(--compose)         сторона требований
                 ├─ host/docker/proxy/panels/         сторона возможностей,
                 │  scheduler/certs/backup + databases в порядке зависимостей
                 └─ witness.Evaluate()              24 правила: находки, изменения, откат
            каждый даёт model.SectionResult: статус, счётчики, длительность, замечания
       └─ report.Commands = runner.Journal()   каждая команда, включая отклонённые
  └─ redact.Report(result)           последнее действие перед любой записью
  └─ report.WriteDir() | WriteCombined() | WriteJSONFile() | WriteJSON()
  └─ report.Upload()                 только при --upload и --upload-token
  └─ код возврата из статусов разделов, либо 3, если отправка не удалась
```

Разделы выполняются в фиксированном порядке, а не в порядке запроса. Раздел
уязвимостей переиспользует инвентарь установленных пакетов, собранный ранее; на
хосте с тремя тысячами пакетов читать его дважды — самая дорогая операция, какую
инструмент мог бы себе позволить. `witness` идёт последним по той же причине: он
читает порты и службы, уже лежащие в отчёте.

Два шага потока стоит прочитать дважды.

**Белый список проверяется внутри `run.Runner`, до поиска бинаря.** Существует ли
команда на этом хосте — не наше дело, пока не установлено, что запускать её
разрешено. Отказ попадает в журнал и в лог уровня error; он никогда не становится
ошибкой, которую коллектор может проглотить.

**`redact.Report` выполняется после всех коллекторов и до любой записи.** Это
последняя линия, а не первая: ни один коллектор не читает секреты намеренно. Она
нужна потому, что отчёт несёт и свободный текст, которого никто не проектировал —
строку cron, командную строку процесса, директиву прокси, — а этот отчёт может быть
отправлен наружу.

## Пакеты

| Пакет | Ответственность |
|---|---|
| `app/config` | Разбор флагов и переменных `AUDIT_*`. Вся валидация здесь, поэтому неверный аргумент падает до запуска первой команды. |
| `app/logging` | Уровневый логгер, пишущий только в stderr. |
| `app/model` | Типы записей, словарь критичности, калькулятор CVSS, разбор `/etc/os-release` и три словаря witness (манифест, возможности, находки). Ни от чего в дереве не зависит. |
| `app/run` | Запуск внешних команд: общий таймаут, `LC_ALL=C`, белый список кодов выхода — и **белый список команд** (`allowlist.go`) вместе с самим списком (`commands.go`) и журналом каждого запуска. |
| `app/redact` | Зачистка учётных данных в готовом отчёте. |
| `app/pkgmgr` | Интерфейс `Manager` и бэкенды apt, dnf/yum, zypper, pacman, apk, плюс компараторы версий dpkg, rpm и общий. |
| `app/vuln` | Типы записей OSV и вычисление диапазонов, загрузчик офлайн-набора, клиент API и слияние трёх источников в одну таблицу. |
| `app/collect/system` | Инвентарь хоста и его защищённость. |
| `app/collect/ports` | Слушающие сокеты из `/proc/net`. |
| `app/collect/services` | Службы из systemd, OpenRC, SysV или таблицы процессов. |
| `app/collect/manifest` | Парсер compose-файла: сторона *требований* witness. Читает один переданный файл и `.env` рядом с ним. О хосте не наблюдает ничего. |
| `app/collect/host` | Архитектура, память, файловые системы вместе с inode и уже установленные базы данных — числами, а не прозой. |
| `app/collect/docker` | Движок контейнеров: сам движок, реализация compose, контейнеры, сети, тома, образы. |
| `app/collect/proxy` | nginx / Apache: эффективная конфигурация, имена серверов с файлом и строкой, порты, пути сертификатов. |
| `app/collect/panels` | Хостинговые панели управления, по фиксированному списку файловых маркеров. |
| `app/collect/certs` | TLS-сертификаты на диске, разбираемые `crypto/x509`, и то, обновляет ли их вообще что-нибудь. |
| `app/collect/scheduler` | Запланированная работа: cron во всех его видах плюс systemd-таймеры. |
| `app/collect/backup` | Инструменты бэкапа, задания бэкапа и дата самого свежего файла в каждом каталоге бэкапов. |
| `app/witness` | 24 правила, список изменений и план отката. Чистые функции от манифеста и возможностей; ничего не наблюдают. |
| `app/report` | Рендеринг CSV через общий помощник `utils/csv`, JSON-документ, общий контракт аудита и отправка. |
| `app/audit` | Оркестрация разделов и кеш общего инвентаря. |

Зависимости направлены в одну сторону: `audit` → коллекторы → `pkgmgr`/`run` →
`model`. Ничто в `model` не импортирует то, что выше, — поэтому компараторы,
калькулятор CVSS и каждое правило witness тестируются без хоста в каком-либо
особом состоянии.

`app/witness` и `app/collect/*` строго разделены, и именно поэтому находку можно
объяснить тому, кто должен по ней действовать: коллектор никогда не судит, а
правило никогда не наблюдает. Единственное исключение — вспомогательная функция:
`app/witness` импортирует `app/collect/host` ради `FilesystemFor`, которая
определяет, под какую файловую систему попадает точка монтирования, а это
арифметика, а не наблюдение.

## Решения, о которых стоит знать

**Бинарь может выполнить ровно один опубликованный список команд.** Не по
соглашению: `run.Runner` отклоняет всё, чего нет в `app/run/commands.go`, включая
аргументы, ещё до поиска бинаря. Добавить команду можно только правкой этого файла
— поэтому она появляется в ревью и в `--commands` одновременно. См.
[09 — Белый список команд и журнал](09-command-allowlist.md).

**Ядро читается напрямую, инструменты — нет.** Сокеты берутся из
`/proc/net/{tcp,tcp6,udp,udp6}`, а не из `ss` или `netstat`. Ни того, ни другого
нет в минимальном образе, а аудит безопасности — неподходящее место, чтобы
добавлять зависимости аудируемому хосту. `ss` остаётся запасным вариантом для
хостов, скрывающих `/proc/net`.

**Сертификаты разбираются в Go, а не вызовом `openssl`.** `crypto/x509` плюс
`encoding/pem` — это десяток строк, результат не зависит от того, какой openssl
несёт хост, и белый список не обрастает записью, о которой читателю пришлось бы
рассуждать. `app/collect/certs` не запускает ни одного подпроцесса.

**Ненулевой код выхода — не автоматически ошибка.** `dnf check-update` выходит с
кодом 100, когда обновления есть. `pacman -Qu` — с 1, когда их нет. `apk version
-l` — с 1 на пустом результате. `systemd-detect-virt` — с 1 на «железе». Считать
любой из них ошибкой значило бы отрапортовать «обновления недоступны» на хосте,
где они прочитаны безупречно, поэтому `run.Runner.OutputAllowExit` принимает коды,
означающие успех для конкретной утилиты.

**`LC_ALL=C` для каждой команды.** Парсеры опираются на английские заголовки
колонок. Русская или немецкая `LC_MESSAGES` переписывает их все.

**Один подпроцесс на хост, а не на пакет.** Определять репозиторий pacman по
одному пакету за раз означало бы процесс на каждый обновляемый пакет — несколько
сотен на rolling-релизе. `pacman -Sl` строит тот же индекс один раз. Та же логика
ограничивает коллекторы witness: `docker image inspect` ограничен 200 образами,
`docker network inspect` — 100 сетями, и если предел срабатывает, об этом
сообщается.

**Ошибки — это значения, идущие вместе с данными.** Коллекторы возвращают то, что
успели собрать, *вместе* с ошибкой и фиксируют проблему через `Note`/`Degrade`
раздела. Ненулевая ошибка никогда не означает пустой результат, а пустой
результат никогда не означает чистый хост.

**Nil-указатель и пустой срез — разные ответы.** `Capabilities.Runtime` равен nil,
когда движка контейнеров нет, и не-nil с `Reachable = false`, когда движок есть, но
не отвечает. Правила действуют по этой разнице, потому что пустой список
контейнеров от недоступного демона читается как «на хосте ничего не запущено».

## Зависимости

Четыре модуля — либо соседи стандартной библиотеки, либо собственные модули
платформы:

| Модуль | Для чего |
|---|---|
| `github.com/BloodHeavenDevelop/utils` | `utils/csv`, общий генератор CSV. |
| `github.com/BloodHeavenDevelop/contracts` | Сгенерированный Go для `bloodheaven.audit.v1` — контракта отчёта, общего с сервисом `witness`. Продублировать форму здесь значило бы узнать о расхождении на первой же отправке. |
| `google.golang.org/protobuf` | `protojson`, чтобы отдать контракт с **именами** перечислений (`SEVERITY_BLOCKER`), а не числами. |
| `gopkg.in/yaml.v3` | Чтение compose-файла как дерева `yaml.Node`, что сохраняет порядок ключей, номера строк и merge-ключи — всё это декодирование в структуры выбрасывает. |

Всё остальное — стандартная библиотека. Общий `utils/logger` платформы сознательно
не используется — почему, написано в [CLAUDE.md](../../CLAUDE.md). `protobuf`
встречается ровно в одном файле (`app/report/contract.go`); больше нигде в
инструменте о существовании protobuf не знают.

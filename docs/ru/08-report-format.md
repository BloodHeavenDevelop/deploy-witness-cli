# 8. Формат отчёта

## Файлы

По умолчанию инструмент пишет один каталог с одиннадцатью файлами:

```
audit-<хост>-<метка UTC>/
├── summary.csv           читать первым
├── system.csv
├── updates.csv
├── vulnerabilities.csv
├── ports.csv
├── services.csv
├── witness.csv         находки
├── evidence.csv          на чём каждая находка стоит
├── changes.csv           что деплой реально сделает
├── rollback.csv          и как это откатить
└── commands.csv          каждая команда, которую прогон выполнил или пытался
```

Последние пять появились в 0.2.0. Четыре из них принадлежат разделу `witness`;
`commands.csv` принадлежит самому прогону и пишется всегда, что бы ни было в
`--sections`.

**Раздел, не давший ни одной строки, всё равно получает файл со строкой
заголовков.** Отсутствующий файл неотличим от раздела, который вообще не
запускался, а разница между «ничего не слушает» и «мы не смотрели» и есть вся
ценность аудита. `commands.csv` следует тому же правилу по той же причине: «этот
аудит не выполнил ни одной команды» должно быть видимым утверждением, а не
отсутствующим файлом.

С `--stdout` те же таблицы пишутся в один поток, каждая с предваряющей строкой
`# <имя>` и пустой строкой-разделителем. И табличные процессоры, и `csvkit` это
читают; одна плоская таблица не вместит одиннадцать разных наборов колонок.

С `--format json` вместо CSV-файлов пишется один `report.json` — см.
[report.json](#reportjson) ниже.

Кодировка — UTF-8, разделитель — запятая, экранирование по RFC 4180. Метки
времени — в UTC. Большинство из них в формате `YYYY-MM-DD HH:MM:SS UTC`; два
исключения отмечены на месте — `commands.csv` не добавляет литерал `UTC`, а время
съёма доказательства пишется по RFC 3339 (`2026-08-17T09:39:13Z`).

**Учётные данные маскируются до любой записи.** Каждое поле со свободным текстом —
строки cron, командные строки процессов, замечания, вывод доказательств, значения
меток манифеста — проходит через `app/redact`, и найденное значение заменяется
видимым маркером `***redacted***`, а не удаляется: `password=***redacted***`
сообщает читателю, что там что-то было, а молчаливое удаление превратило бы
доказательство в ложь. Число изменённых полей логируется: если зачистка срабатывает
на обычном хосте, значит либо коллектор читает лишнее, либо шаблоны слишком жадные,
и знать стоит и то, и другое.

**Колонки только дописываются.** Потребители читают по позиции не реже, чем по
заголовку, поэтому новые колонки добавляются в конец, а существующие не
двигаются.

## summary.csv

Указатель. По строке на раздел, с предваряющей строкой `report`, описывающей
прогон.

| Колонка | Содержание |
|---|---|
| `Section` | `report` либо имя раздела |
| `Status` | `ok`, `partial`, `skipped` или `failed` |
| `Records` | Сколько строк дал раздел |
| `Critical` | Критичные находки (только уязвимости) |
| `High` | Находки высокой критичности (только уязвимости) |
| `Duration` | Сколько раздел работал |
| `Notes` | Всё, что разделу не удалось, через `; ` |

Статусы:

| Статус | Значение |
|---|---|
| `ok` | Раздел отработал полностью |
| `partial` | Дал строки, но столкнулся хотя бы с одной проблемой — читайте `Notes` |
| `skipped` | Не был выбран |
| `failed` | Не дал ничего пригодного |

`partial` несёт нагрузку. Раздел, собравший часть строк и затем упавший, никогда
не отмечается как `ok`, иначе читатель примет усечённую таблицу за полную.

## system.csv

| Колонка | Содержание |
|---|---|
| `Category` | `host`, `os`, `kernel`, `hardware`, `storage`, `network`, `time`, `packages`, `accounts`, `ssh`, `hardening`, `updates` |
| `Key` | Имя факта, например `hostname`, `kernel.kptr_restrict` или точка монтирования |
| `Value` | Значение как прочитано |
| `Source` | Откуда именно оно взято, например `/proc/meminfo`, `sshd -T` |

Колонка `Source` существует, чтобы любую строку можно было независимо проверить
на хосте.

## updates.csv

| Колонка | Содержание |
|---|---|
| `Package` | Имя пакета |
| `Installed` | Установленная версия |
| `Available` | Версия, ожидающая в репозиториях |
| `Arch` | Архитектура, если менеджер её сообщает |
| `Repository` | Origin, например `Debian-Security:12/stable`, `extra` |
| `Security` | `true`, если обновление из канала безопасности |
| `Severity` | Вендорская критичность, если опубликована, иначе `unknown` |
| `Advisory` | Идентификатор бюллетеня, если опубликован |
| `Source` | Команда, из которой получена строка |

## vulnerabilities.csv

Отсортирован от худшего.

| Колонка | Содержание |
|---|---|
| `Package` | Затронутый установленный пакет |
| `Installed` | Установленная версия |
| `Fixed in` | Версия с исправлением, если бюллетень её называет |
| `Severity` | `critical`, `high`, `medium`, `low`, `none` или `unknown` |
| `Score` | Подтверждающая базовая оценка CVSS, например `9.8 (CVSS_V3)` |
| `Id` | Основной идентификатор, CVE если он есть |
| `Aliases` | Все идентификаторы, данные источниками |
| `Summary` | Однострочное описание |
| `Ecosystem` | Экосистема OSV, в которой найдено совпадение |
| `Source` | `distro-metadata`, `offline-db`, `osv-api` либо несколько через `+` |
| `Reference` | Ссылка на бюллетень |

`Source` с двумя источниками означает, что оба нашли уязвимость независимо, —
это более веское свидетельство, чем строка из одного источника.

## ports.csv

Отсортирован по порту.

| Колонка | Содержание |
|---|---|
| `Protocol` | `tcp`, `tcp6`, `udp` или `udp6` |
| `Address` | Адрес привязки |
| `Port` | Порт привязки |
| `Exposure` | `loopback`, `interface` или `all-interfaces` |
| `State` | `LISTEN` для TCP, `OPEN` для несоединённого UDP |
| `PID` | Владеющий процесс, `0` если привязать не удалось |
| `Process` | Имя процесса |
| `User` | Владелец, с откатом на числовой UID |
| `Command` | Командная строка, обрезанная до 200 символов |

Сортировка по `Exposure` выводит наверх поверхность, обращённую в сеть. `PID`,
равный `0`, означает, что процесс не удалось прочитать, а не что сокетом никто не
владеет — для полной привязки запускайте от root.

## services.csv

Отсортирован по имени.

| Колонка | Содержание |
|---|---|
| `Name` | Имя юнита |
| `Description` | Описание юнита |
| `Load` | Состояние загрузки в systemd, например `loaded`, `not-found` |
| `Active` | `active`, `inactive`, `failed` |
| `Sub` | Подсостояние, например `running`, `exited`, `dead` |
| `Enabled` | Автозапуск: `enabled`, `disabled`, `static`, `masked` |
| `Main PID` | Главный процесс, `0` если его нет |
| `User` | Пользователь, от которого работает юнит |
| `Active since` | Время запуска, UTC |
| `Manager` | `systemd`, `openrc`, `sysv` или `process-table` |

`Active` и `Enabled` приходят из разных команд и отвечают на разные вопросы: что
работает сейчас и что запустится после перезагрузки. Служба со статусами `active`
и `disabled` исчезнет при следующей загрузке.

## witness.csv

По строке на находку, отсортировано от худшего, затем по правилу, затем по
собственному порядку правила, затем по субъекту — чтобы два прогона одного аудита
давали один и тот же файл.

| Колонка | Содержание |
|---|---|
| `Code` | Стабильный идентификатор находки, например `witness.port_conflict`. Именно по нему сопоставляет интеграция; полный каталог — [10 — Правила witness](10-witness-rules.md) |
| `Collector` | Какое правило её выдало, например `port-conflict`, `certificate` |
| `Category` | `conflict`, `resource`, `security`, `expiry` или `missing` — какого рода беда, а не насколько она серьёзна |
| `Severity` | `blocker`, `warning` или `info` |
| `Subject` | О чём находка: порт, имя сервиса, путь, домен |
| `Title` | Что не так, в одну строку |
| `Description` | На каком основании, с наблюдёнными числами |
| `Why it matters` | Что сломается, если это проигнорировать |
| `What to do` | Следующее действие |
| `Confidence` | `high`, `medium` или `low` |
| `Evidence` | `N in evidence.csv, first: <команда>` либо `none` |

Три уровня, а не шесть, как в шкале CVE из `vulnerabilities.csv`. Источник
уязвимостей оценивает, насколько плоха уязвимость в абстракции; находка witness
отвечает на другой вопрос — должен ли читатель остановиться:

| Уровень | Значение |
|---|---|
| `blocker` | Уже сломано либо уже эксплуатируемо. Намеренно редкий: ложный блокер останавливает деплой, который прошёл бы нормально, и следующий уйдёт с выключенными проверками |
| `warning` | Настоящая проблема, которая пока ничего не ломает |
| `info` | Стоит знать, ничего не сломано, — включая «эту проверку выполнить не удалось», о чём сообщается, а не умалчивается |

`Confidence` равен `high` только для прямого наблюдения. Всё, что выведено из
отпечатка, индекса или разбора свободного текста, — не выше `medium`.

В `summary.csv` строка `witness` переиспользует два счётчика: `Critical` держит
число блокеров, `High` — число предупреждений, поэтому читатель видит блокеры по
указателю, не открывая раздел.

## evidence.csv

Каждое доказательство под каждой находкой, по строке на штуку. Это отдельный файл, а
не ячейка в `witness.csv`, потому что у находки может быть несколько
доказательств, каждое с многострочным фрагментом, а всё обещание раздела в том, что
читатель может их проверить.

| Колонка | Содержание |
|---|---|
| `Code` | Находка, которую это доказательство подпирает, — соединяйте по нему |
| `Subject` | Субъект находки, чтобы различить несколько строк одного кода |
| `Command` | Что запустить, чтобы увидеть то же самое: команда из опубликованного белого списка, либо путь на диске, либо манифест и сервис (`docker-compose.yml (service db)`) |
| `Output` | Что наблюдалось, компактно, из разобранных значений |
| `Truncated` | `true`, если фрагмент обрезан на 1500 символах. Обрезанный фрагмент, который об этом не признаётся, провоцирует читателя на лишние выводы |
| `Captured at` | RFC 3339, UTC |

**Находка без доказательств не публикуется никогда.** Движок её отбрасывает и
считает отброшенные в замечаниях раздела — как баг `deploy-witness`, а не как свойство
хоста.

## changes.csv

«Что деплой реально сделает» — тот самый раздел, который показывают собственному
клиенту, когда спрашивают, что изменили на сервере. Сознательно конкретный: полные
пути, точные порты, имена контейнеров. Список изменений со строкой «конфигурация
будет обновлена» ничего не стоит для того, кто за это отвечает.

| Колонка | Содержание |
|---|---|
| `Kind` | `container`, `command`, `firewall-port`, `file` или `disk-space` |
| `Target` | Что именно меняется: имя контейнера, ссылка на образ, `8080/tcp`, путь на хосте, точка монтирования |
| `Detail` | Что с ним произойдёт, например `replaced (currently running, image nginx:1.25) with nginx:latest` |

| Kind | Какие строки даёт |
|---|---|
| `container` | По одной на сервис (создан либо заменён — с указанием, что заменяется), плюс по одной на каждую не-external сеть манифеста |
| `command` | Образ, который придётся тянуть, с реестром, откуда он придёт; либо сервис, который собирается локально, с его контекстом сборки |
| `firewall-port` | По одной на каждый опубликованный порт хоста, с указанием, насколько далеко он будет доступен — порт, опубликованный без адреса хоста, попадает на все интерфейсы, и этого как раз не ожидают |
| `file` | Каждый bind-монтаж (с пометкой чтение/запись или только чтение) и каждый именованный том |
| `disk-space` | Сколько места свободно на файловой системе с хранилищем контейнеров и сколько образов ещё предстоит скачать |

Строка про диск сознательно неполна и говорит об этом: сколько нужно отсутствующим
образам, нельзя узнать без обращения к реестру, а этот аудит его не делает.

В `model.ChangeItem` назван и вид `dns-record`, который пока ничем не производится.
Он есть в словаре, но не в выводе.

## rollback.csv

Ответ на «и как мы это откатим». `Available: false` — интересное значение и причина,
по которой это не просто список инструкций.

| Колонка | Содержание |
|---|---|
| `Kind` | `image-tag`, `volume-backup`, `proxy-config` или `snapshot` |
| `Available` | Существует ли это **прямо сейчас** |
| `Detail` | Что это такое или чего именно не хватает |

| Kind | Что проверяется |
|---|---|
| `image-tag` | Записан ли на этом хосте digest каждого сейчас работающего образа. Тега недостаточно: именно тег и сдвинулся |
| `volume-backup` | Есть ли бэкап и свежий ли он — устаревший вернул бы данные в состояние старше, чем кто-либо ожидает |
| `proxy-config` | Всегда `false`: этот аудит не копирует ничью конфигурацию nginx никуда, а прокси, который не поднялся, уносит все сайты хоста, а не только новый |
| `snapshot` | Всегда `false`: существует ли снапшот гипервизора или провайдера, изнутри машины не видно, и сказать это лучше, чем опустить строку |

Находка `witness.no_rollback_plan` поднимается по этой таблице, когда хотя бы одна
строка недоступна.

## commands.csv

Журнал: каждая команда, которую этот прогон выполнил или пытался выполнить, по
порядку. Это не раздел — это то, что прогон *сделал*, а не то, что он нашёл, — и он
пишется при каждом запуске.

| Колонка | Содержание |
|---|---|
| `Command` | Полный argv, склеенный для чтения. Ничто не идёт через шелл, поэтому это описание, а не строка для вставки обратно |
| `Started at` | `YYYY-MM-DD HH:MM:SS`, UTC (без литерального суффикса) |
| `Duration` | С округлением до миллисекунды, например `36ms`, `1.204s` |
| `Exit code` | Код выхода процесса либо `-1`, если ничего не запускалось |
| `Outcome` | `ok`, `failed`, `timeout`, `missing` или `refused` |

| Исход | Значение |
|---|---|
| `ok` | Выход 0 либо один из ненулевых кодов, означающих успех для этой утилиты |
| `failed` | Команда выполнилась и завершилась ошибкой |
| `timeout` | Превысила `--timeout` и была снята |
| `missing` | Бинаря нет на этом хосте. Нормальная ситуация, а не сбой: так инструмент сообщает «этот хост такой утилитой не пользуется» |
| `refused` | Команды **нет в опубликованном белом списке**, и она вообще не запускалась |

**Строка `refused` — это дефект `deploy-witness`, а не свойство хоста.** Она означает,
что коллектор попросил команду, которой нет в опубликованном списке. Она печатается,
а не скрывается, именно потому, что была бы самой важной строкой файла: она же
логируется уровнем error и не меняет код возврата. Сравните этот файл с выводом
`deploy-witness --commands` — их совпадение и превращает «он только читает» из
утверждения в то, что можно проверить. См.
[09 — Белый список команд и журнал](09-command-allowlist.md).

## report.json

С `--format json` инструмент пишет один `report.json` из двух названных половин, и
названия — это и есть смысл:

```json
{
  "schemaVersion": "1.0",
  "upload": { "schema_version": "1.0", "level": 2, "server_fingerprint": "…", "…": "…" },
  "audit":  { "generatedAt": "…", "system": [], "updates": [], "…": "…" }
}
```

| Ключ | Содержание | Уходит с машины? |
|---|---|---|
| `schemaVersion` | Версия контракта половины `upload`. Получатель проверяет её первой, поэтому агент, собранный месяцы назад, получит ответ «твой отчёт не понят», а не будет прочитан наполовину | — |
| `upload` | Общий контракт `bloodheaven.audit.v1` в виде protojson: `findings` с доказательствами, `collectors` (результаты разделов), `changes`, `rollback`, `command_journal`, плюс `level`, `server_fingerprint`, `server_hostname`, `generated_at`, `stale_after` и `producer` | **Да** — это ровно те байты, которые отправляет `--upload` |
| `audit` | Всё, что остаётся локальным: инвентарь хоста, список обновлений, список CVE, разобранный манифест, наблюдённые возможности и те же находки во внутренней форме этого инструмента | Нет |

Клиент может прочитать файл, увидеть, какая половина покинула бы его машину, и
сверить её с тем, что реально пришло. Это куда убедительнее обещания — и разойтись
половины не могут, потому что загрузчик отправляет те же байты, из которых записан
файл, а не собирает второй документ.

Что стоит знать:

- **`server_fingerprint` — солёный SHA-256 от `/etc/machine-id`, а не сам
  идентификатор.** Получателю нужно узнавать один и тот же хост между двумя
  отправками; ему не нужен идентификатор, работающий как ключ ещё к чему-то об этой
  машине. Голый хеш от 32 hex-символов отделён от оригинала одним заглядыванием в
  радужную таблицу, поэтому дайджест солится и становится специфичным для этой
  задачи. Если `/etc/machine-id` не читается, поле остаётся пустым, а не подменяется
  чем-то более слабым.
- **`level` всегда равен `2`** — witness на самом сервере. Уровни 0 и 1 — это
  проверки со стороны домена, они относятся к сервису `witness`.
- **`stale_after` — это `generated_at` плюс 7 дней.** Состояние сервера дрейфует;
  через неделю картина может не держаться, и читателю об этом говорят, а не
  оставляют догадываться.
- **`command_journal` несёт весь журнал**, включая отказы, строками вида
  `команда — исход (длительность)`.
- **Перечисления уходят именами** (`SEVERITY_BLOCKER`, `CATEGORY_CONFLICT`,
  `COLLECTOR_STATUS_PARTIAL`) — именно это разбирает принимающий сервис. `partial`
  отображается в `PARTIAL`, а не в `OK`: сначала он уходил как `OK`, и принимающий
  сервис исправно сохранил прогон, деградировавший на непривилегированном хосте, как
  полный аудит этой машины.
- **Инвентаря пакетов, списка обновлений и списка CVE в `upload` нет.** Контракт —
  это документ находок, а отправлять их значило бы добровольно передавать полный
  инвентарь ПО чьего-то продакшн-хоста сервису, который об этом не просил.

`report.json` пишется с правами `0600` в каталоге `0750`, как и CSV, и с отступами —
отчёт, который клиент должен изучить до отправки, обязан быть читаемым без
форматтера. С `--format json --stdout` тот же документ уходит в stdout.

# 11. Испытательный стенд

Стенд сравнивает то, что CLI **предсказывает**, с тем, что Docker **делает на самом
деле**, в заранее подготовленных ситуациях. Модульные тесты доказывают, что правило
следует своей спецификации ([10 — матрица итогов](10-witness-rules.md#матрица-итогов));
стенд доказывает, что спецификация совпадает с Docker.

```bash
make bench                                   # все сценарии, ~3 минуты
make bench BENCH_ARGS="-only port_conflict"  # сценарии, чей id с этого начинается
```

Одна команда, одна одноразовая среда, один каталог результатов
(`bench/out/<метка UTC>/results.json` и `results.csv`).

## Среда

| | |
|---|---|
| Движок | Один контейнер Docker-in-Docker из **зафиксированного образа** `docker:27.5.1-dind` (Docker Engine 27.5.1, плагин Compose **2.33.0**). Другая версия — `BENCH_ARGS="-image docker:<версия>-dind"`; версии движка и Compose внутри образа записываются в каждый файл результатов |
| Сеть | `--network none`: среда не выходит никуда за свои пределы. Compose не может скачивать образы, поэтому отсутствующий образ или чужая платформа приводят к ошибке, а не к загрузке |
| Образы | Загружаются из движка этой машины (`docker save | docker load`), по умолчанию `alpine:3.21` (`-images`, чтобы сменить). Ничего не скачивается; образ должен быть на машине |
| CLI | Бинарник из `make build`, копируется внутрь. Его `--version` и коммит записываются |
| Привилегии | `--privileged`, без которого Docker-in-Docker не работает. Это единственное, чего стенд требует от машины; контейнер удаляется в конце (`-keep` оставляет его для отладки) |
| Учётные записи | Аудит идёт от `root` или от непривилегированной учётной записи `bench`, у которой нет доступа к сокету движка, — ситуация «недостаточно данных» для каждого правила, зависящего от движка |

## Что делает один сценарий

Каждый сценарий — каталог `bench/scenarios/<правило>/<случай>/`:

| Файл | Содержимое |
|---|---|
| `scenario.yaml` | `id`, `rule` (код находки), `situation` (`problem`, `no-problem`, `unknown`, `manual-check`, `not-applicable`), `description`, `critical`, `audit.user` и `audit.args`, `project`, `expect.outcome` (и `expect.also` для столь же верной альтернативы, объяснённой в описании), `docker.up`, `docker.outcome` (`fails`, `succeeds`, `advisory`) и `docker.pattern` |
| `compose.yml` | План |
| `setup.sh` | Необязательно: готовит ситуацию внутри среды, от root, из каталога сценария — контейнер, держащий порт, том, созданный вручную, более раннее развёртывание |

Обвязка (`bench/dwbench`) для каждого сценария по порядку id:

1. сбрасывает движок до пустого — ни контейнера, ни тома, ни своей сети от прошлого сценария;
2. копирует сценарий внутрь и выполняет `setup.sh`;
3. снимает снимок движка (контейнеры с состоянием и образом, тома, сети) и каталога сценария;
4. запускает аудит — `deploy-witness --compose compose.yml --project-name <проект> --format json <args>` от пользователя сценария — и берёт итог правила из `audit.rules` (JSON-двойника `rules.csv`); код `2` — это предсказание `refused`;
5. снова снимает снимок: любое отличие — **побочный эффект аудита**;
6. выполняет запланированное изменение, `docker compose -f compose.yml -p <проект> <docker.up>` (по умолчанию `up -d`), и через несколько секунд проверяет, что все контейнеры работают, — запустившийся и сразу упавший контейнер означает неудачный деплой, что бы ни вернул `up`;
7. записывает оба вердикта.

## Вердикты

| Вердикт | Значение |
|---|---|
| **прогноз по спецификации** (`specMatch`) | Итог правила равен `expect.outcome` сценария (или одному из `expect.also`). Несовпадение — дефект CLI или спецификации |
| **Docker как ожидалось** (`dockerMatch`) | `docker.outcome: fails` — изменение упало (с `docker.pattern` в выводе, если задан); `succeeds` — прошло и контейнеры остались работать. Несовпадение значит, что сценарий готовит не то, что заявляет, или Docker ведёт себя не так, как предполагает правило |
| `advisory` | Docker это правило не решает (healthcheck, плавающий тег, власть над хостом, резерв памяти): результат записывается, но не оценивается |
| **ошибка стенда** | Отказал сам стенд — сброс, копирование или `setup.sh` не выполнились, аудит не записал отчёт или упал. Сценарий ничего не доказывает о CLI и считается отдельно, никогда не как ошибка CLI |
| **побочный эффект аудита** | Во время аудита что-то изменилось в движке или каталоге сценария. Аудит не должен менять ничего; любая запись — дефект |

Сценарий `unknown` готовит настоящую проблему, которую аудит не видит (движок не
отвечает): Docker тогда падает, как и ожидается, — а `unknown` от CLI **не**
считается обнаружением, и любой показатель качества по прогону обязан считать его
именно так.

## Покрытие

| Правило | Сценариев | Подготовленные ситуации |
|---|---|---|
| `port_conflict` | 9 | чужой контейнер; другой протокол; другой адрес; обновление своего деплоя; движок недоступен; оставленный orphan; orphan удаляется (`--remove-orphans`); динамический диапазон занят целиком / со свободным портом |
| `container_name_conflict` | 3 | чужой; свой; движок недоступен |
| `project_ownership` | 3 | другая копия; этот каталог под другим именем проекта; свой |
| `volume_name_conflict` | 4 | внешний отсутствует / есть; движок недоступен; существует без метки проекта |
| `network_name_conflict` | 3 | внешняя отсутствует / есть; движок недоступен |
| `subnet_overlap` | 3 | пересечение; без пересечения; движок недоступен |
| `bind_path_conflict` | 4 | отсутствует при `create_host_path: false`; существует; создаётся движком; недоступен учётной записи аудита |
| `env_file_missing` | 2 | отсутствует; `required: false` |
| `architecture_mismatch` | 3 | закреплена чужая платформа; образа нет; совпадает |
| `registry_unreachable` | 2 | не проверялось (без `--egress`); соединение отвергнуто (`--egress`) |
| `runtime_missing_or_old` | 2 | движок отвечает; движок недоступен |
| `no_healthcheck`, `privileged_container`, `insufficient_memory`, `floating_image_tag` | 8 | проблема / без проблемы (и неприменимо) — advisory |

Не готовятся, с причиной: `insufficient_disk`, `insufficient_inodes` и
`disk_at_limit` требуют намеренно заполненной файловой системы; `proxy_conflict`,
`domain_conflict`, `database_version_mismatch`, `backup_gap`, `no_rollback_plan`,
`certificate_expiring` и `reboot_required` читают ПО хоста (nginx, БД, certbot,
пакетный менеджер), которого в Docker-in-Docker нет. Их покрывают тесты матрицы
итогов (`app/witness/outcomes_test.go`), а не поведение Docker.

## Что нашёл стенд

Первые прогоны нашли четыре дефекта; они исправлены в том же изменении и теперь
держатся сценариями:

- внешняя сеть, созданная вручную (`docker network create`, без метки проекта),
  выдавалась как «общая с другим стеком» — `network_name_conflict/no-problem-external-present`;
- Compose 2.x печатает `create_host_path` только при `true`, а Compose 5.x — только
  при `false`, поэтому на Compose 2.33 отсутствующий источник с
  `create_host_path: false` читался как создаваемый — `bind_path_conflict/problem-missing-no-create`;
- контейнер, который запускается и сразу падает (образ под другую платформу), давал
  `up -d` с кодом `0`: теперь стенд проверяет, что контейнеры продолжают работать;
- при открытой сети Compose скачал вариант под чужую платформу поверх загруженного
  образа, и все последующие сценарии шли на нём: теперь у среды нет сети.

## Как добавить сценарий

Скопируйте ближайший каталог сценария, поменяйте план и `setup.sh`, задайте
`situation`, `expect.outcome` и `docker.outcome` и прогоняйте его отдельно
(`make bench BENCH_ARGS="-only <id>"`), пока оба вердикта не сойдутся по верной
причине. Каждому правилу нужны три ситуации — проблема, похожая ситуация без неё и
недостаток данных — везде, где среда может их подготовить. `go test ./bench/...`
проверяет, что каждый закоммиченный сценарий загружается и правильно оформлен.

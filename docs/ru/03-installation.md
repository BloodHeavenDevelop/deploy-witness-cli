# 3. Установка

## Требования

- Go 1.25 или новее — для сборки.
- Ничего — для запуска. Бинарь статический (`CGO_ENABLED=0`) и обращается к
  инструментам дистрибутива только если они есть.
- Доступ к **двум** приватным модулям организации:
  `github.com/BloodHeavenDevelop/utils` (ради `utils/csv`) и
  `github.com/BloodHeavenDevelop/contracts` (ради сгенерированного Go для контракта
  отчёта `bloodheaven.audit.v1`, который отправляет `--upload`). Либо они уже в
  кеше модулей, либо настройте доступ к организации:

  ```bash
  export GOPRIVATE=github.com/BloodHeavenDevelop/*
  ```

  Сгенерированный Go закоммичен в `contracts`, поэтому ни `protoc`, ни `buf` здесь
  не нужны. Две публичные зависимости — `google.golang.org/protobuf` и
  `gopkg.in/yaml.v3` — приходят через модульный прокси, как любые другие.

Требования к запуску не изменились: бинарь по-прежнему статический, без
рантайм-зависимостей, и на аудируемом хосте по-прежнему не нужно ничего
устанавливать. Чтение `docker-compose.yml` через `--compose` не требует ни Docker,
ни Compose, ни сети — парсер это `gopkg.in/yaml.v3`, вкомпилированный в бинарь. На
хосте вообще без движка контейнеров раздел `witness` первой же находкой сообщит,
что запускать деплой здесь нечем.

## Сборка

```bash
make build                # ./deploy-witness для текущей машины
make build-linux-amd64    # ./bin/deploy-witness-linux-amd64
make build-linux-arm64    # ./bin/deploy-witness-linux-arm64
make build-all            # обе кросс-платформенные цели
```

Версия, зашиваемая в бинарь, берётся из первого нумерованного заголовка в
`CHANGELOG.md`. Дерево, где верхний раздел ещё `## [Unreleased]`, соберётся с
пустой версией — это ожидаемо, не ошибка.

Сборка без `Makefile` — `go build` или `go run .` — сообщает версию `dev`, потому
что никто её не зашил. Это сделано намеренно: раньше в исходнике стоял номер
релиза, который устаревал в момент выпуска следующего и затем врал в `--version`,
в заголовке `--commands` и в поле `producer` каждого загруженного отчёта. Отчёт не
должен приписывать свои находки релизу, из которого он не собран.

## Запуск из исходников

```bash
make development ARGS="--sections ports,services --stdout"
```

## Установка

```bash
sudo make install         # /usr/local/bin/deploy-witness
```

Либо скопируйте кросс-собранный бинарь на целевой хост — рантайм-зависимостей у
него нет:

```bash
make build-linux-amd64
scp bin/deploy-witness-linux-amd64 server:/usr/local/bin/deploy-witness
ssh server 'sudo deploy-witness --out /var/log/deploy-witness'
```

## Привилегии

Инструмент работает без root и сообщает, до чего не смог добраться. Запуск от
root добавляет ровно это и ничего больше:

| Требует root | Иначе |
|---|---|
| `/etc/shadow` — учётки с пустым или заблокированным паролем | Отмечается как непрочитанный пробел |
| `/etc/sudoers`, `/etc/sudoers.d/*` — правила `NOPASSWD` | Отмечается как непрочитанный пробел |
| `/proc/<pid>/fd` чужих процессов | Сокеты перечисляются без владеющего процесса |
| `nft list ruleset` | Набор правил отмечается как непрочитанный, а не как пустой |
| Сокет движка контейнеров (root либо группа `docker`) | Движок обнаружен, но `Reachable` равен false, и все проверки конфликтов с существующими контейнерами, сетями, томами и образами пропускаются — с явной пометкой, что пропущены |
| `nginx -T` на большинстве дистрибутивов | Прокси откатывается на ограниченный обход дерева конфигурации, а раздел сообщает, что список имён и портов неполон |
| `/etc/letsencrypt` | Сертификаты оттуда не разбираются, поэтому правилу об истечении не с чем работать |
| `/var/spool/cron/*`, `/var/spool/cron/crontabs/*` | Собирается только crontab текущей учётной записи; остальные отмечаются как непрочитанные, а не как отсутствующие |
| Часть маркеров панелей управления | Панель отмечается как не подтверждённая и не исключённая |

Каждый из этих случаев — это `Degrade` с замечанием, поэтому непривилегированный
прогон остаётся пригодным и помечается `partial`, а не становится тихо более узким.

Инструмент ничего не пишет вне каталога отчёта и не меняет состояние системы.
Каждая внешняя команда, которую он вызывает, — это запрос, а полный список команд,
которые он вообще *способен* вызвать, печатает `deploy-witness --commands` — см.
[09 — Белый список команд и журнал](09-command-allowlist.md).

## Расписание

Встроенного планировщика нет: инструмент делает один проход и завершается.
Используйте cron или systemd timer:

```cron
# Ежедневно в 03:00, по каталогу на день.
0 3 * * * /usr/local/bin/deploy-witness --quiet --out /var/log/deploy-witness/$(date -u +\%F)
```

Код возврата осмыслен для автоматизации: `0` — отчёт записан, `1` — записан, но
раздел упал, `2` — записать не удалось, `3` — записан, но `--upload` не смог его
доставить.

Регулярному прогону, который заодно проверяет деплой, нужен только путь к
манифесту:

```cron
# Ежедневно, плюс witness-проверка стека из /srv/app против этого хоста.
0 3 * * * /usr/local/bin/deploy-witness --quiet --compose /srv/app/docker-compose.yml \
  --out /var/log/deploy-witness/$(date -u +\%F)
```

## Права на отчёт

Каталог создаётся с правами `0750`, каждый CSV — `0600`; `report.json` — тоже
`0600`. Отчёт представляет собой разведывательную сводку по хосту (учётные записи,
открытые порты, непропатченные пакеты, а теперь и раскладка самого деплоя) и не
должен быть доступен всем. По той же причине `.gitignore` исключает `*.csv` и
`/audit-*/` — этого достаточно для `report.json`, записанного в каталог по
умолчанию, но не для того, который `--out` положил куда-то ещё внутри репозитория.
С `--format json` указывайте `--out` вне рабочего дерева.

Учётные данные, попавшие в свободный текст (строка cron, командная строка процесса,
директива прокси), маскируются видимым маркером `***redacted***` до любой записи,
поэтому файл можно прикрепить к тикету — но он всё равно остаётся описанием того,
как атаковать хост, и реальная защита это права доступа.

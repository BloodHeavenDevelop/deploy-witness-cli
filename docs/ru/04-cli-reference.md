# 4. Справочник CLI

```
deploy-witness [флаги]
```

Почти каждый флаг также читает переменную окружения с префиксом `AUDIT_`.
Приоритет: флаг, затем переменная окружения, затем значение по умолчанию. Пустая
переменная считается незаданной, а значение, которое не разбирается как булево или
целое, молча откатывается к значению по умолчанию.

У исключений переменной окружения нет совсем:

- `--online`, `--egress`, `--upload` и `--osv-url` — всё, что открывает сеть или
  выбирает получателя данных. Переменная, зашитая в образ, CI-раннер или профиль
  входа, не должна превращать локальный аудит в аудит, который куда-то
  подключается. `AUDIT_ONLINE`, `AUDIT_EGRESS`, `AUDIT_UPLOAD` и `AUDIT_OSV_URL`
  игнорируются; если такая переменная задана, запуск пишет предупреждение с её
  именем и повторяет его в `network.csv`. См. [Сетевое поведение](#сетевое-поведение).
- `--version` и `--commands`, потому что флаг, заставляющий инструмент напечатать и
  выйти, не должен включаться образом или окружением.

`AUDIT_UPLOAD_TOKEN` читается — это секрет, а не переключатель, и действует он
только вместе с набранным `--upload`.

## Вывод

| Флаг | Переменная | По умолчанию | Значение |
|---|---|---|---|
| `--out <каталог>` | `AUDIT_OUT` | `./audit-<хост>-<метка UTC>` | Каталог для отчёта. Создаётся, если его нет. |
| `--stdout` | `AUDIT_STDOUT` | `false` | Писать отчёт в stdout вместо каталога. Диагностика идёт в stderr, поэтому поток можно направлять по конвейеру. |
| `--format <csv\|json\|csv,json>` | `AUDIT_FORMAT` | `csv` | `csv` — каталог таблиц для человека, `json` — один `report.json` для машины, `csv,json` — оба в `--out` из одного прогона. Любое другое значение — и `csv,json` вместе с `--stdout` — отвергается до запуска аудита. |
| `--sections <список>` | `AUDIT_SECTIONS` | все разделы режима | Подмножество `system,updates,vulnerabilities,ports,services,witness` через запятую. Порядок нормализуется — см. ниже. `witness` допускается только в Compose preflight, и Compose preflight обязан его включать — см. [Режимы](#режимы). |
| `--services-all` | `AUDIT_SERVICES_ALL` | `false` | Включать неактивные юниты, а не только запущенные. |

`--sections` приводится к каноническому порядку выполнения независимо от того,
как записан: поздние разделы используют то, что собрали ранние. Раздел
уязвимостей переиспользует инвентарь пакетов, а `witness` — уже собранные
слушающие сокеты и службы, вместо того чтобы собирать их второй раз. Выбрать
`witness` без `ports` можно: раздел понизит свой статус и напишет замечание —
конфликты портов это самое полезное, что у него есть, и список конфликтов, который
никто не заполнял, не должен читаться как короткий.

`--format json` пишет `report.json` **вместо** CSV-файлов. Чтобы получить оба,
используйте `--format csv,json`: таблицы и `report.json` строятся из одного аудита,
поэтому у них одинаковые `Checked at`, PID и время доказательств. Два отдельных
прогона — по одному на формат — это два аудита с разницей в секунды, и они могут
расходиться.

## Режимы

| Флаг | Переменная | По умолчанию | Значение |
|---|---|---|---|
| `--mode <host-audit\|compose-preflight>` | `AUDIT_MODE` | `compose-preflight` при `--compose`, иначе `host-audit` | Вид прогона. Короткие формы `host` и `preflight` тоже принимаются. |

- **`host-audit`** (аудит хоста) — хост сам по себе. Compose-файл не читается,
  раздел witness не выполняется: он вне рамок этого режима. Разделы по умолчанию:
  все, кроме `witness`. Строки `witness` и `preflight` в `summary.csv` имеют статус
  `not-applicable` с замечанием, начинающимся с `host-audit:`, в отправляемом отчёте
  нет коллектора `witness`, и ничто не считает отсутствие сравнения пробелом — см.
  [08](08-report-format.md#summarycsv).
- **`compose-preflight`** — хост плюс сравнение `--compose` с ним. Раздел witness
  выполняется всегда.

Любое сочетание, при котором один режим мог бы сойти за другой, — ошибка
использования (код `2`), и о ней сообщается до сбора каких-либо данных:

| Задано | Почему отказ |
|---|---|
| `witness` в `--sections`, нет `--compose` | Раздел и есть сравнение; без файла сравнивать не с чем. |
| `--mode compose-preflight`, нет `--compose` | То же. Так плановое задание утверждает, что оно — preflight: пропавший `AUDIT_COMPOSE` останавливает прогон, а не превращает его молча в аудит хоста. |
| `--mode host-audit` вместе с `--compose` (или `AUDIT_COMPOSE`) | Аудит хоста не читает Compose-файл; переданный файл был бы молча проигнорирован. |
| `--compose` с `--sections` без `witness` | Preflight без сравнения — не preflight. |
| Путь `--compose` не существует, это каталог или файл нельзя прочитать | У preflight нет входных данных. |
| Файл `--compose` не разбирается (не YAML, верхний уровень не mapping, пустой файл) | То же — проверяется после печати сетевого плана и до первого раздела. **Отчёт не пишется.** |

Файл, который разбирается, но содержит проблемы внутри — один неразборчивый порт,
`include:`, по которому не переходят, — не отвергается: preflight выполняется, а
его строка `witness` получает `partial` с причиной.

Что печатает явно запрошенный preflight (`--mode compose-preflight --compose <файл>
--out ./report`) для каждого испорченного входа — дословно из бинарника 1.3.x; во
всех случаях код возврата `2`, а `./report` не создаётся:

| Вход | Вывод (stderr) |
|---|---|
| файла нет | `deploy-witness: --compose "./missing.yml": the Compose preflight needs a readable Compose file: stat ./missing.yml: no such file or directory` |
| файл нельзя прочитать (права `0000`, без root) | `deploy-witness: --compose "./locked.yml": the Compose preflight needs a readable Compose file: open ./locked.yml: permission denied` |
| каталог | `deploy-witness: --compose "./.": the Compose preflight needs a Compose file, and this is not a regular file` |
| не YAML (`services: [unclosed`) | строка `network: none …`, затем `ERROR the Compose preflight cannot start, the Compose file could not be parsed: <абс. путь>: yaml: line 1: did not find expected ',' or ']'; no report was written` |
| верхний уровень — список | то же, с окончанием `…: expected a compose file at the top level, got a sequence; no report was written` |
| пустой (только комментарии) | то же, с окончанием `…: the file declares nothing; no report was written` |

Первые три случая отвергаются при разборе флагов, поэтому больше ничего не
печатается; последние три — после сетевого плана и до первого раздела.

### Планируемый запуск

Compose preflight проверяет **тот запуск, который вы собираетесь выполнить**, а не
прочтение одного файла. Флаги плана повторяют `docker compose`, а модель
разрешает сам Compose:

```
deploy-witness --compose compose.yml --compose compose.prod.yml \
  --env-file .env.prod --profile web --project-name shop --compose-service api
```

проверяет ровно то, что запустил бы `docker compose -f compose.yml -f
compose.prod.yml --env-file .env.prod --profile web -p shop up api`. До сбора чего
бы то ни было инструмент выполняет `docker compose <те же флаги> config --format json
--no-env-resolution` (команда есть в [списке разрешённых](09-command-allowlist.md)):
файлы сливаются по порядку, применяются env-файлы и профили, `${VARIABLE}`
подставляются из окружения этого прогона, относительные пути разрешаются от каталога
проекта, а имя проекта выбирается по правилам Compose. `config` работает только с
локальными файлами — без демона и без сети. Его вывод содержит подставленные значения;
он разбирается в памяти в требования, которые сравнивают правила (у переменных
окружения — только **имена**), и никуда не пишется. `plan.csv` и `audit.plan` в
`report.json` фиксируют, что проверялось: файлы по порядку, имя проекта и откуда оно
взято, env-файлы, профили и сервисы, кто разрешил модель и его версия, имена
присутствующих переменных `COMPOSE_*`/`DOCKER_*` и движок.

**План привязан к одному движку.** Инструмент читает активный контекст docker CLI
(`docker context show`/`inspect`) и `DOCKER_HOST`. План, который ушёл бы на удалённый
движок (`ssh://`, `tcp://`), отвергается: этот аудит осматривает хост, на котором
запущен, и не может отвечать за другую машину. Ответивший движок записывается по ID и
имени из `docker info`, поэтому два сервера с одинаковыми именами контейнеров не
спутать.

Если Compose здесь не установлен, план из **одного файла** без `--env-file` и
`--profile` читает встроенный разборщик; отчёт говорит об этом, а строки `witness` и
`preflight` — `partial`: приближение никогда не выдаётся за разрешение самого
Compose. План, который встроенный разборщик воспроизвести не может, отвергается.

**Ошибка подготовки плана никогда не становится результатом preflight.** Каждый
случай ниже — код `2`, сообщение после сетевого плана и до первого раздела, отчёт не
пишется:

| План | Почему отвергается |
|---|---|
| `docker compose config` его отвергает (`${VAR:?}` без значения, неизвестный ключ, отсутствующий обязательный `env_file`, сервис неактивного профиля в зависимостях) | Compose отверг бы и запуск; его сообщение цитируется, учётные данные маскируются |
| Файл `include:`-ит удалённый источник (`https://`, `git@`, `oci://`) | Разрешение скачало бы его; положите файл рядом и подключите по пути |
| `DOCKER_HOST` или активный контекст docker указывает на удалённый движок | План — для другой машины |
| `--compose-service` называет сервис, которого нет в разрешённом плане | Такого сервиса нет или его профиль не активирован |
| Compose не установлен, а в плане несколько файлов, `--env-file` или `--profile` | Встроенный разборщик это не воспроизведёт |

## Witness

| Флаг | Переменная | По умолчанию | Значение |
|---|---|---|---|
| `--compose <путь>` | `AUDIT_COMPOSE` (несколько путей через `:`, как в `COMPOSE_FILE`) | нет | Compose-файл планируемого запуска, как `docker compose -f`; для нескольких повторите флаг **в том порядке, в котором деплоите**. С ним прогон становится Compose preflight. Каждый файл проверяется на старте — отсутствующий, нечитаемый или неразбираемый файл это код возврата `2` без отчёта, а не понижение раздела, — а пути приводятся к абсолютным. См. [Планируемый запуск](#планируемый-запуск). |
| `--env-file <путь>` | `AUDIT_ENV_FILE` (через `:`) | нет | Env-файл планируемого запуска, как `docker compose --env-file`; можно повторять. Его читает Compose для подстановки; значения в отчёт не попадают. |
| `--profile <имя>` | `AUDIT_PROFILE` (через запятую) | нет — действует `COMPOSE_PROFILES`, как у Compose | Профиль, который активирует запуск; можно повторять. |
| `--project-name <имя>` | `AUDIT_PROJECT_NAME` | то, что выведет Compose | Имя проекта, как `docker compose -p`. Оно решает, какие существующие контейнеры, сети и тома принадлежат этому деплою, — см. [10 — Имя проекта](10-witness-rules.md#имя-проекта-и-почему-оно-важно). |
| `--project-directory <каталог>` | `AUDIT_PROJECT_DIRECTORY` | каталог первого файла | Как `docker compose --project-directory`: где читается `.env` и от чего разрешаются относительные пути. |
| `--compose-service <имя>` | `AUDIT_COMPOSE_SERVICES` (через запятую) | все сервисы активных профилей | Сервис, который запускает план, как `docker compose up <сервис>`; можно повторять. Его зависимости включаются, как их включает Compose. |
| `--egress` | — | `false` | Разрешить единственную исходящую проверку: TCP-connect к каждому реестру, из которого тянет манифест, — на порт 443 или на порт, указанный в ссылке на образ (`registry.local:5000/app`), — по 5 с на реестр. Доказательство и заметка раздела называют именно тот адрес, к которому подключались. Ни TLS-рукопожатия, ни HTTP-запроса, ни аутентификации, ни запроса манифеста образа. Без флага правило доступности пишет «не проверялось», а не делает выводов. |

Без `--compose` прогон — аудит хоста, и раздел witness вне его рамок (см.
[Режимы](#режимы)); отчёт говорит об этом в строке `report` и в строках
`preflight` и `witness`, обе `not-applicable`.

## Уязвимости

| Флаг | Переменная | По умолчанию | Значение |
|---|---|---|---|
| `--vuln-db <путь>` | `AUDIT_VULN_DB` | нет | Офлайн-набор OSV: файл `.json`/`.jsonl`, `.gz`, zip-экспорт или каталог с записями OSV (обходится рекурсивно). |
| `--online` | — | `false` | Дополнительно запрашивать OSV API и запускать `debsecan` (Debian/Ubuntu) или `arch-audit` (Arch), если они установлены: оба скачивают данные бюллетеней при каждом вызове, поэтому без `--online` они не запускаются, и раздел об этом сообщает. |
| `--osv-url <url>` | — | `https://api.osv.dev` | Базовый URL OSV API. Только вместе с `--online`. Только `https://` (`http://` — лишь для loopback-хоста); редирект не выполняется. |
| `--ecosystem <имя>` | `AUDIT_ECOSYSTEM` | выводится | Переопределить экосистему OSV, например `Debian:12`. Нужно для дистрибутивов, которых OSV не публикует. |
| `--min-severity <уровень>` | `AUDIT_MIN_SEVERITY` | `low` | Отбрасывать находки ниже уровня: `low`, `medium`, `high`, `critical`. Неоценённые не отбрасываются никогда. |
| `--max-osv-lookups <n>` | `AUDIT_MAX_OSV_LOOKUPS` | `1500` | Предел числа детальных запросов за прогон, вместе с `--online`. Если предел сработал, `summary.csv` об этом скажет. |

## Отправка отчёта

| Флаг | Переменная | По умолчанию | Значение |
|---|---|---|---|
| `--upload <базовый-url>` | — | нет | Отправить отчёт в сервис witness. Один `POST` на `<базовый-url>/api/public/audit/upload`, `Content-Type: application/json`, таймаут 30 с, без повторов. Нужен токен. Только `https://` — `http://` принимается лишь для `localhost`, `127.0.0.0/8` или `::1`, для стенда разработки. В URL не должно быть учётных данных, query и fragment. Проверяется до запуска аудита (код `2`). |
| `--upload-token <токен>` | `AUDIT_UPLOAD_TOKEN` | нет | Одноразовый токен, разрешающий отправку. Уходит заголовком `X-Upload-Token`, никогда в URL. Требует `--upload`; из окружения берётся, только если `--upload` набран. |

`--upload` без токена или `--upload-token` без `--upload` — ошибка использования
(код `2`): наполовину настроенная отправка, которая молча ничего не делает, хуже
отказа стартовать.

**Передавайте токен через окружение.** Токен, набранный как `--upload-token`,
остаётся в истории шелла и в `/proc/<pid>/cmdline`, который во время аудита может
прочитать любой локальный пользователь. `AUDIT_UPLOAD_TOKEN` не попадает в список
процессов (окружение процесса читают только его владелец и root). Вводите его без
эха и помните, что `sudo` по умолчанию сбрасывает окружение:

```bash
read -rs AUDIT_UPLOAD_TOKEN && export AUDIT_UPLOAD_TOKEN
sudo --preserve-env=AUDIT_UPLOAD_TOKEN deploy-witness --compose /srv/app/docker-compose.yml \
  --upload https://deploywitness.example.com
```

**Редирект отклоняется, а не выполняется.** Если адрес отвечает `3xx`, отправка
завершается с кодом `3`, а сообщение называет, куда указывал редирект; ни токен, ни
отчёт туда не уходят. Укажите конечный адрес.

**Получатель печатается до отправки**: сетевой план в начале запуска и
`uploading <n> bytes … to <endpoint>` непосредственно перед запросом (оба на уровне
info, поэтому `--quiet` их скрывает).

Отправляется половина `upload` JSON-документа: находки с доказательствами,
результаты коллекторов с их заметками, список изменений, план отката и журнал
команд. В том числе: имя хоста, абсолютный путь к файлу `--compose` (в
доказательствах) и — через журнал — имена образов, сетей, юнитов и локальных
пользователей, с которыми запускались команды. Инвентарь хоста, список обновлений и
список CVE **не отправляются**. Хост опознаётся солёным SHA-256 от
`/etc/machine-id`, а не самим идентификатором — см.
[08 — Формат отчёта](08-report-format.md#reportjson). Прочитайте её заранее через
`--format json`.

При успехе тело ответа сервиса печатается в stdout, если оно непустое. У
DeployWitness это небольшой JSON-документ вида
`{"publicToken":"…","level":2,"findings":8,"refused":0,"hostname":"…"}`; публичный
токен — это ссылка на отчёт, и **любой, у кого она есть, может прочитать отчёт** без
входа.

## Сетевое поведение

Сетевых путей три, и каждый включается только флагом, набранным в командной
строке. Это всё, что инструмент и все запускаемые им команды куда-либо отправляют:

| Режим | Кому | Что отправляется | Где зафиксировано |
|---|---|---|---|
| **По умолчанию** (без сетевых флагов) | Никому. | Ничего. Ни DNS-запросов, ни сетевых сокетов: бинарь использует только netlink (чтобы перечислить адреса интерфейсов этого хоста) и локальные unix-сокеты (D-Bus для `timedatectl`/`systemctl`, сокет docker/podman). Команды, которые скачали бы данные, не запускаются (`debsecan`, `arch-audit`) или привязаны к кешу (`apt-get -s`, `dnf`/`yum -C`, `zypper --no-refresh`). | Строка лога `network: none …`; строка `network` в `summary.csv` = `offline: …`; в `network.csv` все четыре пути с `Enabled=false`, `Contacts=0`. |
| `--online` | OSV API по `--osv-url` (по умолчанию `https://api.osv.dev`). Если установлены: `debsecan` → `security-tracker.debian.org`, `arch-audit` → `security.archlinux.org` — эти адреса выбирают сами утилиты дистрибутива. | OSV: имя, версия и экосистема **каждого установленного пакета** (`POST /v1/querybatch`, по 1000 в запросе), затем по одному `GET /v1/vulns/<id>` на найденный бюллетень, не больше `--max-osv-lookups`; `User-Agent: deploy-witness/<версия>`. Фиды: собственная загрузка данных каждой утилитой (запрос debsecan называет кодовое имя релиза); сравнение с установленными пакетами идёт на этом хосте. | `network.csv`: у `osv-api` число обращений = отправленные HTTP-запросы; у `distro-feeds` = запуски утилит, которые также видны в `commands.csv` с `Network=--online`. |
| `--egress` (нужен Compose preflight) | Каждый реестр из `image:` в compose-файле (`docker.io` для образа без реестра), на порт 443 или на порт из ссылки. | DNS-запрос через системный резолвер, затем один TCP-connect, сразу закрываемый. Ни TLS, ни HTTP, ни байта полезной нагрузки. | `network.csv`: получатели в виде `host:port`, число обращений = подключения; заметка раздела и доказательство находки называют тот же `host:port`. |
| `--upload` | Ровно `<базовый-url>/api/public/audit/upload`, как набрано. | Один `POST`: половина `upload` отчёта (см. выше) и заголовок `X-Upload-Token`. | Строка с получателем до отправки; результат — в stdout и в коде возврата. `network.csv` называет получателя — отправка идёт после записи отчёта, поэтому число обращений там остаётся `0`. |

Общие правила трёх путей:

- **Только набранные флаги.** Ни одна переменная окружения не включает путь и не
  выбирает получателя (см. начало страницы).
- **Только `https://`** для `--osv-url` и `--upload`. Обычный `http://` принимается
  лишь для буквального loopback-хоста (`localhost`, `127.0.0.0/8`, `::1`), где
  ничего не пересекает сеть: стенд разработки или тест. Имя, которое просто
  резолвится в loopback, не считается.
- **Без редиректов.** Ответ `3xx` — ошибка с указанием, куда он вёл; туда ничего
  повторно не отправляется.
- **Сначала получатели.** План пишется в лог до начала аудита, та же таблица
  записывается в `network.csv`.
- **Прокси.** `--online` и `--upload` учитывают `HTTPS_PROXY`/`HTTP_PROXY`/
  `NO_PROXY`; `host:port` прокси печатается рядом с получателем (без учётных
  данных). Через прокси запрос остаётся TLS от начала до конца: прокси узнаёт хост
  назначения, но не содержимое. `--egress` всегда подключается напрямую.

Дочерние процессы:

- `DOCKER_HOST` или `CONTAINER_HOST`, указывающие куда-либо кроме `unix://`-сокета,
  удаляются из окружения каждой команды аудита, с предупреждением: команды docker и
  podman из белого списка спрашивают только локальный движок этого хоста.
  docker-*контекст*, указывающий на удалённый движок, теперь тоже покрыт: аудит
  читает его (`docker context inspect`) и привязывает каждую команду docker к
  локальному контексту по умолчанию (`DOCKER_CONTEXT=default`), с предупреждением.
  В Compose preflight ни то, ни другое не обходится — план, нацеленный на удалённый
  движок, отвергается, см. [Планируемый запуск](#планируемый-запуск).
- `--commands` помечает команды, которые сами выходят в сеть
  (`network: yes — runs only with --online`), а Runner отказывает им в запуске без
  этого флага.

### Как проверить самому

- Прочитайте `network.csv` и строку `network` в `summary.csv`.
- Протрассируйте запуск: `strace -f -e trace=connect,sendto,sendmsg -o trace.txt deploy-witness …`
  и поищите `AF_INET`/`AF_INET6`. При обычном запуске единственные такие строки —
  `sshd -T` из OpenSSH, который проверяет семейства адресов UDP-`connect` на
  `0.0.0.0:65535` / `[::]:65535` и не отправляет ни одного пакета.
- `unshare -rn deploy-witness …` запускает аудит вообще без сети. Это доказывает,
  что он *работает* без сети, но не то, что он не *пытается* в неё выйти: для этого
  нужна трасса.
- В исходниках `app/netpath/static_test.go` роняет тесты, если сетевой API
  появляется в каком-либо файле, кроме трёх сетевых путей.

## Поведение

| Флаг | Переменная | По умолчанию | Значение |
|---|---|---|---|
| `--timeout <длительность>` | `AUDIT_TIMEOUT` | `60s` | Таймаут на команду, например `30s`, `2m`. Должен быть положительным. Команда, упёршаяся в него, попадает в `commands.csv` с исходом `timeout`. |
| `--verbose` | `AUDIT_VERBOSE` | `false` | Логировать каждую проверку. |
| `--quiet` | `AUDIT_QUIET` | `false` | Логировать только ошибки. Приоритетнее `--verbose`. |
| `--commands` | — | — | Напечатать все команды, которые этот бинарь способен выполнить, и выйти. Печатается именно применяемый список; ничего вне него выполнить нельзя. См. [09](09-command-allowlist.md). |
| `--version` | — | — | Вывести версию и выйти. |
| `-h`, `--help` | — | — | Вывести справку и выйти. |

## Коды возврата

| Код | Значение |
|---|---|
| `0` | Отчёт записан. Разделы могут содержать замечания в `summary.csv`. |
| `1` | Отчёт записан, но хотя бы один раздел упал полностью. |
| `2` | Неверные аргументы — в том числе адрес `--upload`/`--osv-url` не `https://`, конфликт режимов или файл `--compose`, который отсутствует, не читается или не разбирается (отчёт не пишется), — либо отчёт не удалось записать. |
| `3` | Отчёт записан, но `--upload` не смог его доставить — в том числе когда адрес ответил редиректом, который никогда не выполняется. |

Статус `partial` не влияет на код возврата — такой раздел всё же дал пригодные
строки. Какие именно — смотрите в `summary.csv`.

`3` приоритетнее `1`: отправка выполняется после записи отчёта, и именно её
провал администратору нужно узнать первым — ведь смысл набранной команды был в
том, чтобы доставить файл. Отчёт при этом всё равно лежит на диске.

Отклонённая команда **не** меняет код возврата. Это дефект самого инструмента, а
не свойство хоста, и он проявляется строкой лога уровня error и строкой `refused`
в `commands.csv`.

## Примеры

```bash
# Аудит хоста: всё о хосте, в каталог с меткой времени. Это не preflight.
sudo deploy-witness

# Что этот бинарь может сделать с моим сервером? Ответ до запуска.
deploy-witness --commands

# Только то, что открыто в сеть, сразу в табличный процессор.
deploy-witness --sections ports,services --stdout > exposure.csv

# Compose preflight: проверить деплой против этого хоста до развёртывания.
sudo deploy-witness --compose /srv/app/docker-compose.yml

# То же для планового задания, которое не должно превращаться в аудит хоста.
sudo deploy-witness --mode compose-preflight --compose /srv/app/docker-compose.yml

# Точный запуск многослойного деплоя: два файла, env-файл, профиль, один сервис.
sudo deploy-witness --compose /srv/app/compose.yml --compose /srv/app/compose.prod.yml \
  --env-file /srv/app/.env.prod --profile web --project-name shop --compose-service api

# Только раздел witness, с проверкой доступности реестров.
sudo deploy-witness --sections ports,services,witness \
  --compose /srv/app/docker-compose.yml --egress

# Один JSON-документ, чтобы администратор прочитал, что именно ушло бы наружу.
sudo deploy-witness --compose /srv/app/docker-compose.yml --format json

# Тот же прогон, с доставкой в сервис witness. Код 3 — записан, но не отправлен.
# Токен берётся из окружения и не появляется в списке процессов.
read -rs AUDIT_UPLOAD_TOKEN && export AUDIT_UPLOAD_TOKEN
sudo --preserve-env=AUDIT_UPLOAD_TOKEN deploy-witness --compose /srv/app/docker-compose.yml \
  --upload https://deploywitness.example.com

# Только критичные находки, по офлайн-экспорту OSV.
sudo deploy-witness --vuln-db /var/lib/osv/all.zip --min-severity critical

# Все три источника уязвимостей сразу.
sudo deploy-witness --vuln-db /var/lib/osv/all.zip --online

# На Arch — принудительно указать экосистему, которую OSV публикует (см. 07).
deploy-witness --sections vulnerabilities --ecosystem Arch --vuln-db ./arch-osv/

# Без присмотра, тихо, с проверкой кода возврата вызывающей стороной.
deploy-witness --quiet --out /var/log/deploy-witness/$(date -u +%F) || echo "аудит неполный"
```

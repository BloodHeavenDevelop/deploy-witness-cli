# 6. Коллекторы

## system

Плоская таблица строк `category, key, value, source`. Это именно таблица
ключ-значение, а не структура на каждую тему: машина с необычной раскладкой
просто даст меньше строк вместо того, чтобы навязывать всем пустые колонки. Факт,
который не удалось прочитать, опускается, а не додумывается.

| Категория | Источник |
|---|---|
| `host` | `os.Hostname`, `hostname -f`, `/etc/machine-id`, `systemd-detect-virt`, маркеры контейнера (`/.dockerenv`, `/run/.containerenv`, `/run/systemd/container`) |
| `os` | `/etc/os-release` (запасной — `/usr/lib/os-release`) |
| `kernel` | `/proc/sys/kernel/{ostype,osrelease,version}`, `uname -m`, `/proc/uptime`, `/proc/loadavg` |
| `hardware` | `/proc/cpuinfo`, `/proc/meminfo`, `/sys/class/dmi/id` |
| `storage` | `/proc/mounts` + `statfs(2)` по каждой точке монтирования |
| `network` | `net.Interfaces`, `/etc/resolv.conf`, `/proc/net/route` |
| `time` | Симлинк `/etc/localtime`, `timedatectl show` |
| `packages` | Обнаруженный пакетный менеджер |
| `accounts` | `/etc/passwd`, `/etc/shadow`, `/etc/sudoers`, `/etc/sudoers.d/*` |
| `ssh` | `sshd -T`, с откатом на разбор `sshd_config` |
| `hardening` | `/sys/fs/selinux/enforce`, `/sys/module/apparmor/...`, `systemctl is-active`, `nft list ruleset`, пятнадцать значений `/proc/sys` |
| `updates` | `/var/run/reboot-required`, `needs-restarting -r` |

Замечания по отдельным проверкам:

- **Диски: псевдо-ФС и readonly-образы пропускаются.** `squashfs`, `iso9660` и
  `erofs` исключены наравне с `proc`, `sysfs`, `tmpfs` и прочими: snap-монтирование
  по построению всегда заполнено ровно на 100%, и десяток таких строк похоронил бы
  настоящие тома под ложными «диск полон». Свободное место считается по `Bavail`,
  а не `Bfree` — зарезервированные для root блоки не являются ёмкостью, доступной
  сервису.
- **`sshd -T` предпочтительнее чтения файла.** Он разворачивает директивы
  `Include`, блоки `Match` и вкомпилированные значения по умолчанию. Ручной разбор
  `sshd_config` не видит ничего из этого и отрапортует отсутствие
  `PasswordAuthentication` на хосте, где его включает drop-in файл. Если `sshd -T`
  недоступен, используется откат, а раздел помечается `partial`.
- **Учётки с UID 0 перечисляются поимённо.** Вторая учётная запись с UID 0 —
  бэкдор для повышения привилегий, о котором ни один пакетный менеджер не сообщит.
- **Sysctl безопасности приводятся как есть, без оценок.** Безопасное значение
  `net.ipv4.ip_forward` на маршрутизаторе является опасным на сервере приложений;
  отчёт излагает факты и оставляет политику читателю.
- **Файрвол без читаемого набора правил — не файрвол без правил.** Подсчёт правил
  требует `CAP_NET_ADMIN`; без него раздел сообщает, что набор прочитать не
  удалось, а не рапортует ноль.

**Требует root:** `/etc/shadow`, `sudoers`, `nft list ruleset`.

## updates

По строке на каждый обновляемый пакет, из метаданных, уже лежащих на диске.
**Ни один репозиторий не обновляется** — это сетевая операция, а на Arch частичная
синхронизация является документированным способом сломать систему.

| Менеджер | Запрос | Определение канала безопасности |
|---|---|---|
| apt | `apt-get -s -q dist-upgrade` | Строка origin содержит `security` |
| dnf / yum | `dnf -C -q check-update` | `dnf -C -q updateinfo list --security --with-cve` |
| zypper | `zypper --non-interactive list-updates` | через `list-patches` в разделе уязвимостей |
| pacman | `pacman -Qu` | не публикуется |
| apk | `apk version -l '<'` | не публикуется |

`apt list --upgradable` сознательно не используется: он не называет origin, а
origin — единственный способ отличить обновление безопасности от рядового без
доступа к сети.

## ports

Слушающие сокеты, читаемые из `/proc/net/{tcp,tcp6,udp,udp6}` и привязываемые к
процессам обходом `/proc/<pid>/fd` в поисках ссылок `socket:[inode]`.

- **TCP:** только состояние `0A` (LISTEN).
- **UDP:** только несоединённые сокеты. UDP-сокет с удалённым узлом — это клиент,
  а не слушатель.
- **Адреса** в этих таблицах шестнадцатеричные, каждое 32-битное слово в порядке
  байт хоста, а порт — big-endian. Декодировать оба одинаково — классический путь
  к тому, чтобы отрапортовать `1.0.0.127`.

Каждая строка несёт класс **exposure** — именно он превращает список сокетов в
аудит: база на `127.0.0.1` и та же база на `0.0.0.0` — один и тот же сервис и
совершенно разные риски:

| Exposure | Значение |
|---|---|
| `loopback` | Привязан к `127.0.0.0/8` или `::1`; доступен только с этого хоста |
| `interface` | Привязан к одному конкретному адресу |
| `all-interfaces` | Привязан к `0.0.0.0` или `::`; доступен на каждом интерфейсе |

**Требует root** для привязки сокетов чужих пользователей к процессам. Без него
сокеты всё равно перечисляются, а число непрочитанных процессов фиксируется в
замечании.

## services

Запущенные службы. `--services-all` расширяет выборку до всех известных юнитов.

| Init-система | Источник |
|---|---|
| systemd | `systemctl list-units` — состояние сейчас, `list-unit-files` — автозапуск, `systemctl show` — главный PID, пользователь и время запуска |
| OpenRC | `rc-status --all` |
| SysV | `service --status-all` |
| нет | `/proc`, процессы, переподчинённые PID 1, помечаются `manager=process-table` |

Текущее состояние и автозапуск читаются двумя разными командами намеренно: служба
может быть запущена сейчас и отключена при загрузке, и именно в этом смысл
колонки `Enabled`.

`systemctl show` вызывается порциями по 100 юнитов, чтобы список аргументов
оставался далеко внутри `ARG_MAX` на хостах с тысячами юнитов. Время запуска
приводится к UTC.

## witness

Единственный раздел с двумя сторонами. `app/collect/manifest` читает, чего
деплой **требует**; семь коллекторов читают, что **предлагает** хост;
`app/witness` их сравнивает. Первые два ничего не судят, третий ничего не
наблюдает — именно это позволяет объяснить находку тому, кто должен по ней
действовать.

Сами правила и все коды находок — в
[10 — Правила witness](10-witness-rules.md).

### Сторона требований: `app/collect/manifest`

Один файл на диске — тот, что назван в `--compose`. Ни одной команды, ни одного
сокета, ни одного обращения к реестру: этот коллектор так же локален, как и весь
остальной инструмент.

| Что читается | Откуда |
|---|---|
| Сервисы, в порядке файла | `services:` — образ (разобранный на реестр/репозиторий/тег/digest), `build`, `container_name`, `platform`, `ports`, `expose`, `volumes`, `networks`, `network_mode`, `depends_on` (обе формы), `restart`, наличие `healthcheck`, память и CPU из `deploy.resources`, `privileged`, `cap_add`, `devices`, `extra_hosts`, `dns`, `labels` |
| Окружение | **Имена** переменных из `environment:`, а для `env_file:` — путь и то, существует ли он |
| Сети, тома | `driver`, `external` и явные IPAM-подсети сети |
| Подстановка | `${VARIABLE}` — сначала из окружения процесса, затем из `.env` рядом с compose-файлом; это приоритет самого Compose |

Что он сознательно не читает:

- **Значения переменных окружения — никогда.** `environment:` даёт только имена.
  `env_file` даёт путь и факт его существования; содержимое не открывается. `.env`
  рядом с compose-файлом читается исключительно для подстановки `${VARIABLE}` — его
  ключи и значения не собираются, не возвращаются и не попадают в отчёт.
- **Другие compose-файлы.** `include:` фиксируется предупреждением, а не
  разворачивается: этот коллектор разбирает тот один файл, который ему дали, и
  манифест, недополучивший включённое, обязан об этом сказать.

Поддержаны оба синтаксиса портов (`"8080:80"` и длинная форма) вместе с
диапазонами, оба синтаксиса томов, суффиксы памяти, YAML-анкоры и merge-ключи
(`<<: *base`, которыми реальные compose-файлы пользуются активно). Файл читается
как дерево `yaml.Node`, а не декодируется в структуры, поэтому сохраняются порядок
ключей и номера строк, а поле неожидаемой формы можно зафиксировать и пропустить,
не роняя документ.

**Неразрешённая `${VARIABLE}` никогда не заменяется молча на пустую строку.**
Именно так `${DB_PORT}:5432` превращается в `:5432`, что читатель уже ни к чему не
привяжет. Литерал остаётся, а предупреждение называет переменную. Каждое такое
предупреждение появляется дважды: в `Manifest.Warnings`, который едет вместе с
отчётом, и через `Degrade`, чтобы раздел нельзя было назвать полным. Требование,
которое не поняли, — не требование, которое выполнено.

**Требует root:** ничего. Нужен доступ на чтение compose-файла, который
`--compose` проверяет на старте.

### Сторона возможностей

Семь коллекторов идут в порядке зависимостей, потому что три из них читают
результат более раннего: `panels` читает службы, `certs` нужен инвентарь заданий от
`scheduler`, чтобы отличить установленный инструмент обновления от реально
работающего обновления, а `host.Databases` читает слушающие сокеты.

#### `app/collect/host`

| Что читается | Откуда |
|---|---|
| Архитектура | `uname -m` — чем хост *является*, а не под что собран этот бинарь; при эмуляции это разные вещи, и именно об этом случае говорит находка о несовпадении архитектур |
| Память | `/proc/meminfo`: `MemTotal`, `MemAvailable`, `SwapTotal` |
| Файловые системы | `/proc/mounts` + `statfs(2)`, **вместе с inode** |
| Базы данных | Уже собранные слушающие сокеты плюс каталог данных распознанного движка: `postgres`, `mysql`, `mariadb`, `mongodb`, `redis` или `unknown` |

Раздел system сообщает почти то же самое прозой — «использовано 7.5 GiB из 30 GiB
(25.1%)» хорошо читается и бесполезно для правила, — поэтому этот коллектор даёт те
же наблюдения числами и из тех же источников. Ничто не измеряется дважды и ничто не
вычитывается обратно из предложения.

**Inode собираются потому, что деплой может исчерпать их задолго до того, как
заполнит байты.** Образ контейнера — это тысячи мелких файлов; отчёт, показавший бы
только ёмкость, называл бы хост здоровым вплоть до отказа, а отказ выглядит как «no
space left on device» при том, что `df` показывает свободное место.

**Ни к одной базе данных никто не подключается.** Какой движок, какая версия, какой
порт, привязан ли он дальше loopback и сколько диска занимает каталог данных — всё
это видно снаружи. В момент, когда инструмент аутентифицируется в чьей-то
продакшн-базе, чтобы ответить на вопрос, ответ на который можно было просто
увидеть, он перестаёт быть аудитом. Порт, похожий на базу, но обслуживаемый
неизвестным процессом, отмечается как `unknown`, а не угадывается.

**Требует root:** формально ничего, но без прав нельзя войти в каждую точку
монтирования и в каждый каталог данных. Точки монтирования, которые не удалось
измерить, перечисляются в замечаниях и отсутствуют в отчёте, а не додумываются;
обход каталога данных, остановленный раньше времени, сообщает, что размер — частичная
сумма.

#### `app/collect/docker`

| Что читается | Откуда |
|---|---|
| Движок и версии | `docker version`, `docker info` и эквиваленты podman |
| Реализация compose | `docker compose version --short` (плагин), `docker-compose version --short` (standalone V1), `podman-compose version --short` |
| Контейнеры | `docker ps -a --format {{json .}}` — включая остановленные, с их опубликованными портами и метками проекта/сервиса Compose |
| Сети, тома | `... network ls`, `... volume ls` плюс `network inspect` для подсетей |
| Образы | `... image ls --all --digests` плюс `image inspect` для архитектуры, ОС и размера |

Каждая команда — запрос. Ни одна ничего не запускает, не останавливает, не тянет и
не удаляет.

**Окружение контейнера не читается.** `docker inspect` **контейнера** отсутствует в
белом списке именно поэтому: ни имена, ни значения переменных работающего контейнера
не собираются.

**«Движка нет» и «движок не отвечает» — разные ответы.** Первый оставляет
`Capabilities.Runtime` равным nil. Второй ставит `Reachable = false`, добавляет
замечание и понижает статус раздела, потому что пустой список контейнеров при
недоступном демоне читается как «на хосте ничего не запущено» — и даёт список
конфликтов, выглядящий успокоительно коротким.

`image inspect` ограничен 200 образами, `network inspect` — 100 сетями; образы с
одним id инспектируются один раз, поэтому репозиторий с пятью тегами стоит один
вызов. Если предел срабатывает, об этом сообщается.

**Требует root** (или членства в группе `docker`) для доступа к сокету движка. Без
этого движок обнаруживается, `Reachable` равен false, а отчёт сообщает, что все
проверки, связанные с контейнерами, пропущены.

#### `app/collect/proxy`

| Что читается | Откуда |
|---|---|
| Эффективная конфигурация | `nginx -T`, либо `apachectl -S` / `apache2ctl -S` / `httpd -S` |
| Версия | `nginx -v`, `apachectl -v` и аналоги |
| Запасной путь | Ограниченный обход дерева конфигурации, когда дамп недоступен |

**Эффективная конфигурация спрашивается, а не восстанавливается.** `nginx -T`
разворачивает каждый include, каждый симлинк в `sites-enabled` и всё, что панель
перегенерировала прошлой ночью. Самодельный обход `/etc/nginx` не видит ничего из
этого, поэтому обход существует только как запасной путь — а он и случается без
root — и когда он используется, отчёт говорит, что список неполон, а не подаёт
частичный ответ как всё, за что отвечает этот сервер. Обход ограничен глубиной 8,
256 файлами, 4 MiB на файл и 1000 именами серверов, и каждый сработавший предел
фиксируется замечанием.

**Каждое имя сервера несёт файл и строку, где оно настроено.** «Этот домен уже
обслуживается на хосте» полезно лишь тогда, когда читатель может открыть vhost.

**Собираются *пути* сертификатов, а не их содержимое** — и никогда приватный ключ
или `.htpasswd`. Разбор сертификатов — работа `app/collect/certs`.

Когда установлены и nginx, и Apache, инспектируется только nginx; второй
называется в замечании, а статус раздела понижается — `model.Proxy` вмещает один
фронтенд, и молча выбросить второй значило бы скрыть порт, который тот может
держать.

`nginx -v` печатает в stderr, который runner не перехватывает, поэтому на
большинстве хостов разрешённая команда не даёт ничего, и версия читается из строки,
вкомпилированной в бинарь, — ограниченное чтение файла, уже лежащего на диске.

**Требует root** для `nginx -T` на большинстве дистрибутивов (он читает всё дерево
конфигурации, включая файлы под `/etc/nginx`, недоступные всем). Без root ждите
запасной обход и статус `partial`.

#### `app/collect/panels`

Обнаруживает Plesk, cPanel/WHM, DirectAdmin, ISPmanager, Coolify, CapRover,
Portainer, aaPanel, HestiaCP, VestaCP, Virtualmin, Webmin, CyberPanel и ISPConfig.

Панель значит несоизмеримо больше, чем те несколько каталогов, которые её выдают:
она владеет портами 80 и 443, перегенерирует конфигурацию веб-сервера по своему
расписанию и молча отменяет ручные правки. Vhost, добавленный руками на хосте с
Plesk или cPanel, живёт ровно до следующей перегенерации шаблонов. Деплой,
спланированный без знания о панели, — это деплой, который откатит софт, о котором
никто не вспомнил.

Обнаружение сознательно дешёвое и сознательно осторожное: делается `stat` по
фиксированному списку путей — без обходов — и не более одного
`systemctl is-active` на юнит уже найденной панели. Coolify, CapRover и Portainer
поставляются контейнерами, а не пакетами, поэтому они распознаются и по именам
контейнеров, о которых уже сообщил движок, с тегом образа как версией — это
свидетельство лучше каталога данных, который панель вполне может пережить.

**Маркер, который могло оставить и другое ПО, отмечается как выведенный.** Каталог
данных переживает удаление пакета, а unit-файл доказывает лишь то, что пакет когда-то
ставили, — поэтому присутствие, установленное только по слабым маркерам, так и
сообщается, с указанием маркера, вместо утверждения, что панель установлена. Порты —
документированные значения по умолчанию плюс перенесённый админ-порт там, где
панель пишет его в файл.

**Требует root** для части маркеров. Путь, для которого не удался `stat`, понижает
статус раздела с замечанием, что панель нельзя ни подтвердить, ни исключить — это
наблюдалось на непривилегированном прогоне под Arch, где
`/var/lib/docker/volumes/portainer_data` был недоступен.

#### `app/collect/certs`

| Что читается | Откуда |
|---|---|
| Сертификаты | Ограниченный обход фиксированного списка корней: `/etc/letsencrypt/{live,archive}`, `/etc/ssl/certs`, `/etc/pki/tls/certs`, `/etc/nginx/{ssl,certs}`, `/etc/apache2/ssl`, `/etc/httpd/{ssl,conf/ssl.crt}` и хранилища сертификатов панелей (Plesk, HestiaCP, VestaCP, DirectAdmin, ISPmanager, cPanel) |
| Разбор | `crypto/x509` + `encoding/pem` — **ни одного подпроцесса** |
| Владелец обновления | Конфиги обновления certbot, записи `acme.sh`, пути `lego` либо панель |
| Задание обновления | Запланированные задания, собранные `app/collect/scheduler` |

**Различие между *инструментом* обновления и *заданием* обновления — смысл этого
коллектора.** «certbot установлен» и «этот сертификат будет обновлён» — разные
утверждения, и их смешение — ровно тот способ, которым сертификат истекает на хосте,
где инструмент был всё это время: пакет стоял, таймер никто не включил, а каждый
отчёт писал «управляется certbot». Поэтому `Manager` фиксирует, кто выдал файл или
владеет им, а `AutoRenew` выставляется только тогда, когда реально найдено
запланированное задание, запускающее этот инструмент.

**Каталоги приватных ключей перечисляются по имени и никогда не открываются.**
`/etc/ssl/private` и `/etc/pki/tls/private` перечисляются, чтобы читатель видел
наличие ключа; инструменту, читающему ключи, приходится доверять вместо того, чтобы
его проверять.

Пределы: глубина 4, 512 файлов-кандидатов, 512 KiB на сертификат. Файл, который не
разобрался, называется (до пяти таких, дальше — сводка с числом), а не молча
пропускается. Сертификаты CA, найденные через системное хранилище доверия,
пропускаются с подсчётом — это корневые сертификаты дистрибутива, а не
сертификаты, которыми хост что-то обслуживает.

**Требует root** для чтения сертификатов под `/etc/letsencrypt`, который на каждом
дистрибутиве принадлежит только root. Без root правилу об истечении будет не с чем
работать, и раздел об этом скажет.

#### `app/collect/scheduler`

Cron прячется в большем числе мест, чем помнит кто угодно, и читаются все они:

```
/etc/crontab                 системный crontab, с полем пользователя
/etc/cron.d/*                drop-in'ы, тоже с полем пользователя
/etc/cron.{hourly,daily,…}   скрипты, запускаемые run-parts, а не строки crontab
/var/spool/cron/*            пользовательские crontab'ы (раскладка RHEL)
/var/spool/cron/crontabs/*   пользовательские crontab'ы (раскладка Debian/SUSE)
/var/spool/at*               одноразовые задания at
systemd-таймеры              systemctl list-timers плюс show для владельца
```

**Пользовательские спул-каталоги доступны только root.** Без прав этот коллектор не
находит пользовательских заданий, кроме `crontab -l -u <текущая учётная запись>`, и
сообщает об этом через `Degrade`, а не возвращает короткий список, читающийся как
полный. «Заданий cron нет» и «нам не дали посмотреть» — разные ответы.

**Задание `at` подсчитывается, но его команда не публикуется.** Спул-файл `at`
несёт всё окружение отправившего шелла, и это не то, что стоит копировать в CSV.

**Каждая публикуемая команда зачищается от учётных данных в момент разбора
строки**, общими шаблонами `app/redact` — один набор шаблонов в бинаре, а не два
расходящихся. Cron — самое надёжное место на Linux-хосте, где встречается
пароль в открытом виде: `mysqldump -pS3cret`, `PGPASSWORD=… pg_dump`,
`restic -r sftp://user:pass@host/repo`.

Пределы: 256 KiB на crontab, 512 записей на каталог, 2000 заданий всего; каждый
сработавший предел фиксируется.

**Требует root:** `/var/spool/cron/*` и `/var/spool/cron/crontabs/*`.

#### `app/collect/backup`

Три разных вида свидетельств, сознательно разведённых:

| Поле | Свидетельство | Сила |
|---|---|---|
| `Tools` | Установлен инструмент бэкапа (restic, borg, borgmatic, duplicity, rsnapshot, rclone, kopia, pgbackrest, veeam, snapper, timeshift и ещё десяток) | Слабое само по себе: установленный restic, которого никто не вызывает, — не бэкап |
| `Jobs` | Что-то запланированное похоже на запуск бэкапа, взято из вывода scheduler | Сильнее: это уже намерение |
| `Locations` | Что-то записано, **и вот дата самого свежего файла** | То, что может противоречить первым двум, и обычно противоречит |

Инструмент дампа (`mysqldump`, `pg_dump`, `mongodump` и родня) публикуется, но с
пометкой: его наличие ничего не доказывает, он приходит вместе с клиентским
пакетом. Реальное свидетельство — строка cron, которая его вызывает.

Каталоги проверяются независимо от того, установлен ли инструмент: `/backup`,
`/backups`, `/var/backups`, `/srv/backup`, `/mnt/backup` плюс до восьми путей
репозиториев, взятых из запланированных заданий. Ночной `tar | ssh` пишет в
`/backup` с тем же успехом, что и restic.

**Ни один файл бэкапа не открывается.** Размеры и времена изменения берутся из
`stat`; содержимое не читается, не разбирается и не публикуется. Дата — весь смысл:
именно она отличает живой бэкап от заброшенного, и именно поэтому каталог
`/backup`, самый свежий файл в котором четырнадцатимесячной давности, — это находка,
а не повод успокоиться.

Когда ни одно из трёх ничего не нашло, это реальное и достойное отчёта состояние
хоста — «на этой машине нет бэкапов» — и оно идёт в замечание как утверждение, а не
как ошибка.

**Требует root** для входа в большинство каталогов бэкапов и для того, чтобы видеть
запланированные задания других учётных записей.

## Что реально проверено на живой машине

Юнит-тесты покрывают парсеры на фикстурах: парсер compose, парсеры `nginx -T` и
`apachectl -S`, таблицу сигнатур панелей, обход сертификатов, парсеры cron, логику
свежести бэкапов, сопоставитель белого списка, шаблоны зачистки и каждое правило
witness. Ни одному из них не нужен хост в особом состоянии.

Сами коллекторы проверяются запуском инструмента, и честное положение дел такое:

- **Только Arch.** Каждый коллектор, добавленный для раздела `witness`, прогнан
  на реальном хосте с Arch, с правами root и без них, с установленным Docker.
  Бэкенд `pacman` точно так же остаётся единственным пакетным бэкендом, проверенным
  на живой системе.
- **Бэкенды apt, dnf, zypper и apk** написаны по документированным форматам вывода,
  и перед тем, как на них полагаться, их стоит подтвердить на реальном хосте
  соответствующего семейства.
- **Apache, podman, все панели управления и все инструменты бэкапа** распознаются по
  документированным раскладкам и файловым маркерам, а не по машине, где они были
  установлены. У парсеров есть фикстуры; у обнаружения не было встречи с
  оригиналом. Панель или инструмент, которых коллектор не заметил, отражаются как
  «ничего не найдено» — а это ровно та форма пробела, о которой говорит второе
  обещание, — поэтому пустой список `Panels` на хосте, где вы подозреваете панель,
  считайте поводом проверить руками.
